# 扩展点清单（给未来的功能预留的位置）

这份文档回答一个问题：**我要加一个新功能，应该插在哪里？要动哪几处？哪些地方碰不得？**

它存在的理由很实际：这个插件的地图文档是**用户的数据**（存在他们自己的 `.map.md` 文件里），
结构一旦封闭，加功能就会变成"要么丢数据、要么写迁移"。所以"保持开放"不是口号，
而是一份**可执行的接口约定** —— 每次加功能都按这张表落位，就不需要事后大改。

> 用法：动手前先在这里找到对应的那一节，照它列的"要动哪几处"改；
> 收工时回来更新这一节（加功能的代价变了，就说明结构变了）。

---

## 1. 已经开放的部分（可以直接用，不用改结构）

| 能力 | 位置 | 为什么它够开放 |
|---|---|---|
| 每帧渲染计划与绘制分离 | `src/render/renderPlan.ts` → `src/render/MapOverlay.ts` | 加"一层画什么"只需在 plan 里多一段取数（数据形状不同，无法表驱动），**不需要碰命中测试** |
| 图层描述表（显示层与数据层） | `src/render/layerVisibility.ts` → `LAYER_TABLE` | 一行一层（名字 / 提示 / 出厂默认 / 是否数据层 / **绘制次序** / 可选**绘制钩子**）：面板开关、设置页、图例分段、`renderPlan` 的开关判断、`MapOverlay.drawPlan` 的绘制循环**全部遍历它**。加一层实测只改表里 19 行、其余文件 0 行（详 §3.2） |
| 覆盖层与手势分离 | `MapOverlay` 挂在 `div.canvas` 第一个子节点；手势在 `view.containerEl` 捕获阶段 | 覆盖层永久 `pointer-events: none`，所以新增可视化不会挡住原生 Canvas 交互 |
| 未知值原样保留 | 地形 `t` / 标记 `icon` / 路径 `type` / 区域 `type` | 不认识的 ID **保留 + 告警「已保留」**，回退视觉归绘制层。别的库/别的版本写下的东西不会被改写 |
| 自定义定义目录 | `terrainCatalog` / `markerCatalog` / `pathTypeCatalog` / `regionTypeCatalog` | 四类都是"内置 + `custom:` 前缀 + 上限 + 三级回退"的同一模式，新增定义不需要改解析层 |
| 定义文件导入导出 | `src/render/resourceBundle.ts` | `version` + `sections`（文件里**真的出现过**哪几段）+ "段缺失 ≠ 段为空"，所以以后加段不会清空老用户的定义 |
| 文档版本 | `MAP_DOCUMENT_VERSION` + 解析侧拒绝更高版本 | 未来结构变化时，老版本插件会**明确拒绝**而不是"尽力解析"后丢字段 |

## 2. 不可破的约束（每次加功能都得重新确认）

1. **覆盖层永远 `pointer-events: none`**；命中测试与手势只在 `view.containerEl` 上做。
   破了这条，原生 Canvas 的拖动/框选/卡片菜单就会坏。
2. **用户数据只增不改**：不认识的 ID / 字段一律原样保留 + 告警。历史上这条被违反过四次
   （未知 `icon` 被改写成 `town`、未知路径 `type` 让**整条路径消失**、设置页字符串被静默换成出厂值…），
   每次都是用户数据受损，见 `ENGINEERING-NOTES.md` §5.11 / §5.26 / §5.33。
3. **一个设置只有一个来源**（§5.12）：旧字段迁移后只能当镜像，不许第二处读它做渲染。
4. **样式改动只影响新对象**：已画对象把参数存在地图文件里，改设置不许改动它们。
5. **四道门**：`node scripts/build.mjs` → `tsc --noEmit` → `node --test --test-isolation=none` → `node scripts/smoke.mjs`。
   新断言必须有**鉴别力**（把实现改坏，它得变红），见 §5.24。
6. **任何"粘贴进来的带行号正文"都会被构建拒绝**（`scripts/lib/sourceSanity.mjs`，§5.32）。
7. **留好接口，以便后续开发**（2026-09-28 新增，用户明确要求）。这条不是"多加抽象"，而是加功能时**自问一句**：
   **"下一个同类东西来的时候，我要改几处？"**
   - 能写成**登记表**的就写成登记表（选中种类 / 图层 / 字段规格 / 筛选规则 / 地形标签 / 生物群系分类）；
   - 能做成**纯函数 IR** 的就做成 IR（画布与导出共用同一份几何，别写两份绘制）；
   - 需要"以后能整表替换"的，**别把数据写死在代码里**（分类表、色带预设、单位表、标签表）；
   - 命名空间与前缀**留给用户自定义**（`custom:`），内置保持裸 ID；
   - 结构性变化先落**迁移链**（`[v1→v2, …]` 纯函数），不要到处撒 `if (version === …)`；
   - **判断标准**：加一个同类东西，理想是**加一行**；超过三处就在本文档记下"这次为什么做不到"，
     并把接缝（哪个表、哪个钩子、哪个 IR）留出来。
   - 反面例子（本仓库真实发生过）：`resourceBundle` 曾"全仓无调用点"、`fieldPlan` 的图元 IR 一度没有消费者、
     `TerrainCell.f`（旋转/镜像/变体位）已买却没人消费 —— 它们最终都被后续轮次用上了，
     但**当时若没写清"这是留给谁的接口"，下一个人就得靠猜**。留下接口时顺手写一句"给未来的谁用"。

## 3. 未来功能 → 该插在哪里

### 3.1 新增一种"地图对象"（例如温度带对象、深度层对象）

**现状**：新增的选中模型是**表驱动**的 —— 命中顺序、显示名、信息字段、可用动作集中在
`SELECTION_KINDS`（`src/editor/MapEditor.ts` 或 `src/ui/MapPanel.ts` 里的那张表，见对应提交）。
侧栏检查器与高亮都从这张表读。

**要动哪几处**：
1. `src/data/mapDocument.ts`：加一个顶层数组（例如 `bands: []`）＋ `parseXxx` / `serialize` 一段；
2. `SELECTION_KINDS` 加**一行**（显示名、命中优先级、`describe()`、`actions`）；
3. `src/render/renderPlan.ts` 加一段"这一层要画什么"，`MapOverlay` 加一次绘制；
4. 图例（`legend.ts`）与 Base 行（`mapRows.ts`）各加一个分支（这两处是"给人看的清单"，无法完全表驱动）。

**别做**：不要在 `MapPanel` / `MapOverlay` 里写 `switch (kind)` 的长分支 —— 那是这次特意避免的形状。

### 3.2 新增一个"显示/数据图层"（温度带、深度分层…）

**现状（已开放，2026-09-27 起）**：图层由**一张描述表**驱动 —— `LAYER_TABLE`
（`src/render/layerVisibility.ts`，一行一层：`id / label / hint / describe / defaultVisible /
isDataLayer / order / draw?`）。`LAYER_KEYS`、`DEFAULT_LAYER_VISIBILITY`、面板开关、设置页、
图例分段、`renderPlan` 的开关判断、`MapOverlay.drawPlan` 的绘制次序**全部由它派生或遍历**；
`order` 是画布叠加次序的唯一来源，由单测与冒烟各钉一条（防止"地形盖住路径"这类回归）。
持久化形状没变（`data.json` 里仍是 `layers: { terrain: true, … }`，旧数据照旧读、迁移仍幂等）。

**落位时要动哪几处**（**实测：加一个数据层 = 两行 + 三处小配置**）：
1. **`LAYER_TABLE` 加一行** —— 元数据 8 行 + 绘制钩子（约 11 行）；
2. **`OVERLAY_FIELDS` 加一行**（`overlayFields.ts`）—— 读哪个格键、名字、单位、出厂色带，
   外加**必须回答**的 `numeric`：这个字段的值是不是一个数（温度 / 深度是；生物群系那种**分类 ID** 不是）。
   它决定"哪些字段有每格默认值（§B）与加减乘除笔刷（§E）"，
   刻意写成**必填**：漏写会被 tsc 拦住，而不是悄悄多出一个"数值默认值"入口。
   两处都是"纯配置"，`LAYER_KEYS` / 出厂默认 / 面板开关 / 设置页 / 绘制次序**都不用碰**
   （温度层已按这条路走过一遍，见 `ENGINEERING-NOTES.md` §5.45）；
   若这个字段还要"每格默认值"，**一行都不用改**：对话框的行由 `numericDefaultRows()` 从字段表派生；
3. 若这一层还要产出**渲染计划**（连续场 / 等值线这类）—— 现在的答案是**不用动 `renderPlan`**：
   数据层的几何走 `overlayPlan.ts` 的图元清单（画布与导出共用），
   与"分层画什么"的 `renderPlan` 是两条互不干扰的路（2026-09-28 第三轮收口，见 §5.51）；
4. 数据层的值要在 cell 上有位置 —— `temp` / `depth` 已经就位（见 3.5），新字段要进 `KNOWN_CELL_KEYS`；
5. 只有**测试里写死的层数**要跟着改（有意留的提醒，不是结构阻碍）。

**判断标准**：加完这一层，面板开关 / 设置页 / 图例 / 绘制次序**一行都不用改**（温度层已验证）。

### 3.3 新增一类"自定义定义"（例如"温度带定义"）

**现状（阻碍）**：四类 catalog 是**同一模式的四份实现**（各 400–600 行，结构几乎一字不差）。

**定义管理界面的现状（A3 之后）**：四类定义的**新增 / 删除 / 改 ID** 集中在
`src/ui/DefinitionManagerModal.ts` —— 一个弹窗里用 `createCollapsibleGroup(...)` 分成
**四个默认收起**的组（`role` 依次 `terrain / marker / pathType / regionType`），
每组各自渲染"列表 + 改 ID + 删除 + 新增"，**共用同一套渲染骨架**。
入口只有一处：`main.ts` 的 `buildActions()` 里 `id: 'manage-definitions'`（`group: 'def'`），
它同时出现在侧栏面板与命令面板。参数编辑仍留在 `SettingsTab`（那是"新对象默认值"，不是定义）。

**落位时**：抽一个"定义目录"工厂（`id / label / 参数表 / 上限 / 前缀 / 三级回退`），四类改成配置；
新的第五类只写配置 + 一处 `SELECTION_KINDS` 行 + `DefinitionManagerModal` 里加一组
（**渲染骨架复用，不要第五份手写**）。
**别做**：在抽象之前先复制第五份 —— 一旦有了两份以上真实使用者，抽象的形状才是被证据支持的。

### 3.4 视图旋转

**现状（阻碍）**：投影假设"**等比缩放 + 平移**"——
`projection.scale` 是单个数字（`renderPlan.ts`），换算写成 `world = left + rasterX / deviceScale`
（隐含矩阵 `a = d = scale, b = c = 0`）。

**落位时要动哪几处**：
1. 把投影抽象成**完整 2×3 仿射矩阵**（含旋转项 `b` / `c`），世界↔屏幕与命中测试**只走它**；
2. 命中测试（路径/区域的 `hitTestShape`、标记的包围盒）改用逆矩阵；
3. 标签与标记要**反向旋转**保持直立（否则文字会跟着地图转，读不了）；
4. 导出（`mapPreview.ts`）与 Base 缩略图决定是否跟随旋转 —— 这是产品决定，不是技术决定。

**风险**：这是渲染核心，回归面最大。落位时务必先加"旋转 0°"的断言，确认**现有行为一字不变**再加 90°。

### 3.5 一格多值（温度 + 深度 + 地形同时存在）

**现状（2026-09-28 第五轮起：温度 / 深度 / 连续场（栅格 + 内联 PNG）/
工程图式等值线标注（沿线排字 + 真断线 + 对比色）/ 导出叠加层都已端到端跑通）**：

- `TerrainCell = { t?, f?, c?, temp?, depth?, extra? }` —— **一格多值**已经是数据层的事实：
  `t` 变成**可选**（"只有温度 / 深度、没有地形"的格合法），`temp` / `depth` 是**正式字段**
  （**没有取值范围**：任何有限数都是合法数据，越界只体现在颜色上，见 §5.46），未知键仍按 §4 摊平保留；
- 侧栏检查器已经有**「数据层」**一组（字段表里 `group: 'data'`，与「外观」分开渲染）；
- ✅ **温度已经有 hex 覆盖层 + 图例色带栏**：字段表（`overlayFields.ts`）+ 绘制钩子（`overlayDraw.ts`）
  + 图层表一行 + 设置页「数据层」组（色带 / 越界两端 / 不透明度 / 写数值）+ 图例的 `kind: 'ramp'` 条目。
- ✅ **深度照抄了同一套**，并且多了"**值怎么读**"这一层（唯一的新抽象）：
  `OverlayFieldSpec.units` + `OverlayStyle.unit` + `spec.format`，渲染与图例都只走
  `formatFieldReading(spec, value, style, calibration)`；**地图级 `elevation` 标定段**与 `grid` 同级，
  展示单位（米 / 千米 / 相对值）住插件设置。加**第三个带单位的字段**只需在 `OVERLAY_FIELDS` 里
  声明 `units` 与 `format`，渲染 / 图例 / 设置页下拉都不用改（详 §5.48 / §5.49）。
- ✅ **导出侧的内联口径**（2026-09-28 第五轮定稿，`DATA-LAYER-PLAN-v5.md` §0 D1）：
  **不内联用户库内的图片**（外部依赖、可能几十 MB）；**派生的、有上限的**栅格**可以**内联 ——
  连续场的颜色面就是一张内联 PNG（`pngEncode.ts`，分辨率上限 `MAX_FIELD_DIMENSION = 256`），
  并且有一条**体积上限**：内联 data URL 超过 `OVERLAY_RASTER_MAX_CHARS`（128 KiB）时，
  这一层**整层退回逐格多边形**（换一种显示方式重新问一次 `buildOverlayPlan`，没有第二份几何），
  走哪条路由 `buildMapPreviewSvgWithReport` 的 `overlays` 带出来、写进导出提示。
- ✅ **每格默认值**（§B，2026-09-28）：地图文件顶层 `dataDefaults`（键 = 字段的 `cellKey`），
  **兜底只影响渲染**（真值优先、文件里的格不动、清空即删键）。加字段时**不用改这里**，
  但要在字段表那一行回答 `numeric`（见 §3.2 第 2 条）。
- **还没做的**：生物群系与自动推导（`climateModel` 的签名窗口见 §3.3）、
  等值线标注的**避让**（每层最多 3 个、不避让地标文字；沿线旋转与真断线已实现，见 §5.55）、
  导出侧"要不要写逐格数值"的界面开关（目前只有一个 API 开关，默认关）。

**落位时要动哪几处**（数据、温度与深度都已就位，下面是"下一个字段"要动的）：

1. `OVERLAY_FIELDS` 加一行 + `LAYER_TABLE` 加一行 —— 见 §3.2（**两行配置**）；
   若这个字段有自己的单位/读法，再在这一行里加 `units` 与 `format`；
2. **想清楚合成规则**（谁在谁上面、怎么混）并写进 `order` 与注释，别让绘制层临场决定；
3. 若用连续场而不是逐格上色，图元 IR 已经就绪（`fieldPlan.ts` 的 `buildFieldPlan`）；
4. Base 行 / 导出 / 图例都要能表达"这一格还有别的值"（图例分段已在 §3.2 的表里就位）；
   若这一层要进**导出**，只需在 `mapPreview` 的叠加层循环里出现（它按 `OVERLAY_FIELDS` 遍历）——
   **不要再写一份绘制**：几何与配色都来自 `buildOverlayPlan`（§5.51）；
5. 若它需要**地图级元数据**（像深度要标定），照 `elevation` 段的样子加：
   `MapDocument` 一个可选段 + `KNOWN_TOP_LEVEL_KEYS` 一个键 + 解析 / 序列化各一处
   （**老地图没有这一段就一个字节都不多写**）。

## 4. 数据保全是底线（已实现）

> 这一节是"加新图层之前必须先确认"的：它们不改变任何现有行为，但**没有它们，未来加的结构会在老版本里被抹掉**。

| # | 能力 | 状态 | 依据 / 断言 |
|---|---|---|---|
| 1 | **文档顶层未知段落原样保留** | ✅ **本来就已实现**（2026-09-27 更正：本文档初稿误标为"待修"，原因是我当时只 grep 到 `document: {...}` 字面量，没看紧邻的 `extra` 处理） | `parseMapDocument` 收集未知键 → `document.extra`；`serializeMapDocument` 先写未知键再写已知键（`KNOWN_TOP_LEVEL_KEYS` 防覆盖）；回归断言在 `tests/mapDocument.test.ts` 与 `tests/unknownFields.test.ts` |
| 2 | **格（cell）上未知字段原样保留** | ✅ **已修**（2026-09-27）：`TerrainCell.extra` + `KNOWN_CELL_KEYS` + `cellToJson()` | `tests/unknownFields.test.ts`：保留值/嵌套结构、**写回是摊平的**（文件里不许出现 `"extra"` 键）、已知键 `t/f/c` 规则不变、告警只发一次 |

**两条同一口径**：解析时把不认识的键**原样收进 `extra`**，序列化时**摊平写回**（文件里的形状仍是平铺的键，
不是嵌套的 `extra` —— 嵌套等于把数据搬到别的版本不认的位置），并给**一条聚合告警**（列出未知键名，不按格刷屏）。

**为什么这两条是加新图层的前提**：以后往格上或文档里加 `temp` / `depth` / `bands` 时，
老版本插件打开再保存**不能**把它们删掉。这是"用户数据只增不改"在**结构层**的体现
（此前四次事故都发生在字段层，见 `ENGINEERING-NOTES.md` §5.11 / §5.26 / §5.33）。

## 5. 每加一个功能的固定流程

1. 设计：先说清"影响面"（改哪些文件、动到用户数据吗），牵涉用户文件的要先给影响面再动手；
2. 实现：纯逻辑优先放进不 `import 'obsidian'` 的模块（便于单测）；
3. 断言：单测（纯函数）＋ 冒烟（端到端，跑真实打包产物）；
4. **鉴别力**：至少破坏一处实现，确认对应断言变红，再还原（"没红"也要如实报告）；
5. 四道门 → 部署到测试库 `E:\ObsidianPulgins\test-vault` → 给用户**可判伪**的手动清单；
6. 文档轮：README / `USER-MANUAL` / CHANGELOG / `ENGINEERING-NOTES` ＋ 更新本文档；
7. 版本：结构性变化（文档格式、定义文件格式）必须升版本号并在 CHANGELOG 里写明兼容策略。
