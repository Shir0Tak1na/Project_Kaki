# Phase 0 实测结果（Obsidian 1.13.7）

> 本文档记录真实环境下的探针结果，并列出**由数据驱动的设计修订**。
> 设计文档 [TECHNICAL-DESIGN-v2.md](./TECHNICAL-DESIGN-v2.md) 中与本文冲突之处，以本文为准。
>
> 实测环境：Obsidian **1.13.7**（desktop, Windows）· 画布 `Maps/World.canvas`
> 探针实现：`src/dev/diagnostics.ts`（P1/P2/P4）与 `src/dev/viewport-watch.ts`（P3）

---

## 0. 结论摘要

| 问题 | 实测结论 | 影响 |
|---|---|---|
| 覆盖层挂在哪 | **`div.canvas`**（wrapper 的子元素，唯一矩阵缩放等于当前 scale 的世界层） | 采用策略 A；但判据必须修正（见 §3） |
| 坐标怎么换算 | `client = 原点 + scale × world` 的**纯相似变换**（轴对齐）；原点走闭式推导 | 新增 `core/projection.ts`；中心公式降级为兜底 |
| **谁有噪声** | **变换矩阵/`scale` 精确；`posFromEvt` 的输出被量化到整整 1 个 CSS 像素**（噪声上界 0.707 px，与 dpr 无关） | 缩放取矩阵、原点多点标定、运行时走纯闭式路径、判定阈值噪声感知（见 §2.6） |
| 缩放字段用哪个 | **`scale`**（线性比例）；`zoom` 是 `tZoom` 的**别名**，不是比例 | 修正设计文档 §1.1 的错误描述 |
| 重绘怎么触发 | `markViewportChanged` 可补丁；但**逐帧触发**（6 次手势 = 168 次回调） | 必须做视口去重 + 逐帧合并（见 §5） |
| 私有 API 是否够用 | 1.13.7 上**全部存在**，且比逆向类型记录的更多 | 适配层能力齐备，可进入 Phase 1 |

## 1. P2：私有字段探测

`view.canvas` 上实际存在的成员（`arity` 为函数形参个数）：

| 类别 | 字段 | 备注 |
|---|---|---|
| 变换 | `tx` `ty` `tZoom` `zoom` `scale` | ⚠️ `zoom` 与 `tZoom` 数值**逐位相同**（别名） |
| DOM | `wrapperEl` `canvasEl` `moverEl` `canvasRect` `backgroundPatternEl` `edgeContainerEl` | 全部可用 |
| 数据 | `data` `nodes` `edges` | 本次为 2 节点 / 1 边 |
| 视口 | `markViewportChanged()` `requestFrame(1)` `requestSave(1)` `markDirty(1)` `getViewportBBox()` | 均可补丁/调用 |
| 坐标 | `posFromEvt(1)` `posFromClient(1)` `setViewport(3)` | `setViewport(tx, ty, tZoom)` |
| 视图操作 | `zoomToBbox(1)` `zoomToFit()` `getViewportNodes(1)` `deselectAll()` | 可用于"缩放到地图范围" |

**修订**：设计文档 §1.1 原表把 `zoom` 列为缩放比例 —— 错误。正确关系是
`scale = 2^tZoom`，且 `zoom === tZoom`。适配层一律用 `scale` 字段或矩阵的 `a` 分量，
**禁止**使用 `zoom`。

`canvasRect` 给出的是**未变换的视口尺寸**（本次 681×724，与叶子内容尺寸一致），
可以直接用于计算可见世界范围。

## 2. P4：坐标换算（本轮最有价值的发现）

### 2.1 现象：偏差是纯平移，不是比例错误

首轮诊断用"中心公式"（`world = (screen - 中心)/s + t`）与 `posFromEvt` 对照，五组样本的
偏差在**世界尺度**上约 927.8，但换算回像素后恒为 `(298.9, 287.1)` —— 恰好等于
`div.canvas` 矩阵的平移分量 `(299.375, 287.988)`。

| client (px) | posFromEvt → world | 中心公式 → world | Δ（世界） |
|---|---|---|---|
| 719.5, 446.9 | 169.31, 179.05 | −499.83, −463.61 | 927.769 |
| 795.6, 527.8 | 339.45, 360.38 | −329.47, −282.51 | 927.766 |
| 871.7, 446.9 | 509.58, 179.05 | −159.10, −463.61 | 927.442 |
| 719.5, 608.7 | 169.31, 541.71 | −499.83, −101.41 | 928.091 |
| 886.9, 624.9 | 543.16, 577.53 | −125.03, −65.19 | 927.130 |

**诊断**：公式的**形态**正确、**基线**错了。旧实现用 `canvasEl.getBoundingClientRect()`
作为屏幕基线，而 `.canvas` 是视口大小的盒子、其内容被 `transform` 变换，
`getBoundingClientRect()` 返回的是**变换后**的包围盒 —— 因此基线整体偏了一段矩阵平移。

### 2.2 反推：变换是纯相似变换

对每个样本计算隐含原点 `origin = client − world × scale`：

```
(643.870, 366.919)   (643.969, 366.819)   (644.072, 366.919)
(643.870, 366.720)   (644.272, 366.919)
```

**散布仅 0.4 px**（受报告 1 位小数精度限制，见 §6）。这证明模型就是：

```
client = origin + scale × world          (scale = 0.44669732651951655, origin ≈ (644.0, 366.9))
```

### 2.3 闭式关系（可作兜底）

| 量 | 值 |
|---|---|
| wrapper 视口矩形左上角 | (344.6, 78.9) |
| 矩阵平移 `(e, f)` | (299.375, 287.988) |
| 两者之和 | (643.975, 366.888) |
| 由数据反推的原点 | (644.0, 366.9) |

即 `origin = wrapperRect.topLeft + matrix(e, f)`，吻合到 **0.03 px**。
这条关系只来自一次实测，故在实现中**只作为 `posFromEvt` 不可用时的兜底**，
并由诊断持续校验其偏差（`derivedOriginDelta`）。

### 2.4 修订

- 新增 `src/core/projection.ts`：用**锚点 + 缩放**表达投影，不做任何原点推导：

  ```
  client = anchorClient + (world − anchorWorld) × scale
  ```

  锚点由 `posFromEvt`（语义已由本次实测确认：接受 `clientX/clientY`）给出，
  缩放由变换矩阵的 `a` 分量给出。
- 诊断 §5 改为**三方对照**（`posFromEvt` / 锚点投影 / 中心公式），并自动判定中心公式是否可用。
- `posFromClient` 与 `posFromEvt` 语义一致性由 `crossCheckDelta` 持续校验。

### 2.5 第二轮实测：`posFromEvt` 的输出被**量化**（§2.2 的结论需要修正）

第二轮报告（同一画布，视口尺寸 681×724 → 688×730）显示：锚点投影在锚点处 Δ=0，
但离锚点越远偏差越大（0.92 → 1.39 → 1.69 世界单位），**这不像恒定噪声，而像缩放不匹配**。
对被替换掉的旧假设做了一次拟合检验（用报告中的 5 组样本）：

| 检验 | 结果 |
|---|---|
| 映射是否为轴对齐仿射 | ✅ 是。`world.x` 只依赖 `client.x`（耦合项 6.1e-7 ≈ 0），反之亦然 |
| 最佳**对角仿射**最小二乘的残差 | ❌ 仍达 **0.75 世界单位（0.34 px）** —— 说明 `posFromEvt` 不是精确仿射 |
| 两两组合反推的缩放 | ❌ 散布 **0.4387 ~ 0.4482（±1.5%）** —— 远超仿射模型允许的误差 |
| 拟合出的缩放 vs 矩阵缩放 | 横向差 0.16%、纵向差 0.01% —— 差异本身就是噪声量级 |

**唯一自洽的解释**：`posFromEvt`（或它读取的几何）被**量化**。
散布量级 0.34–0.75 px 与"半个量化步长"同量级。第二轮时我把它归因于设备像素取整
（当时假设 `devicePixelRatio = 1.5`），**单位猜错了** —— 第三轮直接测出了真相（§2.6）。

> 也就是说：**变换矩阵与 `scale` 字段是精确的，`posFromEvt` 才是有噪声的那一个。**
> 这正好与 §2.2 的隐含假设相反 —— 上一轮我把它当权威来源、把矩阵当"可能有截断误差的字符串"。

由该结论导出的实现策略（已落地）：

1. **缩放取变换矩阵的 `a` 分量**，绝不从采样点反解（量化会让反解产生 ±1.5% 散布）。
2. **原点用多点中位数标定**（视口内 5×5 网格 + 5 个留出样本），
   而不是单点锚点。单点误差上限是半个量子，多点在统计上显著更优（有蒙特卡洛测试覆盖）。
3. **运行时走闭式路径**：`origin = wrapperRect.topLeft + matrix(e,f)`，来自精确 CSS 值，
   **不含量化抖动**（标记在平移时不会抖）。
4. 诊断新增 **§6 量化探测**：以 0.25 px 步长密集采样（步长必须小于量子，
   否则最小步长只是量子的整数倍，函数会自报 `resolved=false`）。
5. 所有判定阈值改为**噪声感知**：只有超出量化步长才判为异常。

### 2.6 第三轮实测：量化粒度 = **整整 1 个 CSS 像素**（决定性）

第三轮的量化探测（200 个样本/方向，步长 0.25 CSS px）给出干净结果：

| 方向 | 量子（世界单位） | 量子（CSS px） | 重复样本 | 已解析 |
|---|---|---|---|---|
| 水平 | 3.165932 | **1.000001** | 149/200 | ✓ |
| 垂直 | 3.165932 | **1.000001** | 150/200 | ✓ |

同时报告 `devicePixelRatio = 1.6500000953674316`，即一个设备像素 = 0.606 CSS px。
**因此量化粒度是一个 CSS 像素，与显示器缩放无关** —— 第二轮"设备像素"的假设方向对、单位错。

**噪声上界**：每轴半个量子，二维合成 `1 × √2/2 = 0.707` CSS px。
在当前缩放（0.3159）下即 1.58~1.93 世界单位。

**这个数字立刻纠正了我上一轮的一个错误决定**：上一轮我把"标定原点 − 闭式原点"
（当时 0.634 px）当作偏差**施加到了运行时路径上**。但 0.634 < 0.707，它落在噪声上界之内，
**不构成"闭式关系有偏"的证据** —— 施加修正等于往平滑的闭式路径里注入噪声。已撤销：

- 运行时原点 = **纯闭式**（不含任何标定修正）；
- 标定结果只用于**报告与排查**（`agreementDelta`），并明确标注"在噪声内 ⇒ 不施加修正"；
- 新增 `quantumNoiseBound()` 作为统一的判定基准，冒烟测试里加了一条对照场景
  （人为给闭式原点加 4/−3 px 偏移），验证判定能正确区分"噪声内"与"真有偏差"。

**副产品**：`posFromEvt` 只有 CSS 像素精度，意味着**无法**从它获得亚像素定位。
对本插件无实质影响 —— 地形按格吸附（格宽 40 世界单位，误差占比 <5%），
标记定位误差上界约 0.6 px。

## 3. P1：挂载点

实测 DOM（`canvas-wrapper node-insert-event mod-animating`，transform: none）：

```
wrapper (none)
├── svg                        (none)      背景图案
├── div.canvas-card-menu       matrix(1,0,0,1,-71.9744,0)   ← 纯平移
├── div.canvas-controls        (none)      缩放控件
└── div.canvas                 matrix(0.446697,0,0,0.446697,299.375,287.988)  ← 世界层 ★
    ├── svg                    (none)      边
    ├── div.canvas-node        matrix(1,0,0,1,-420,-260)    ← 纯平移
    └── div.canvas-node        matrix(1,0,0,1,220,40)       ← 纯平移
```

**首轮诊断的 bug**：报告列出了 4 个带 transform 的元素并建议"选最浅的"，
那会选中 `canvas-card-menu`。**判据必须是**：

1. 结构证据：该元素的子树是否包含 `.canvas-node`（与缩放无关，最可靠）；
2. 缩放证据：矩阵的 `a`（与 `d`）分量是否等于当前 `scale`；
3. 反向排除：类名包含 `canvas-node` / `canvas-card-menu` / `canvas-control` 的扣分。

已按此实现（`probeTransformCandidates` + `pickWorldHost`），并在冒烟测试中**复刻真实 DOM**
把"不误选菜单/节点"变成回归测试。

**结论**：采用策略 A —— 覆盖层挂到 `div.canvas` 内部。
注意 `wrapper` 带 `mod-animating` 类，说明缩放/定位存在动画；由于 `markViewportChanged`
逐帧触发，自持变换（策略 B）也能跟随动画，但策略 A 更省事且天然同步。

## 4. 其它实测细节

- **`mod-animating`**：`canvas-wrapper` 上存在动画修饰类，`zoomToBbox`/`zoomToFit` 会走动画路径。
- **`moverEl` 为 null、`canvasEl` 即 `div.canvas`**：适配层原先把 `moverEl` 排在 `canvasEl` 之前优先，
  本次实测该字段不存在 —— 兜底链已保留（`moverEl → canvasEl → wrapperEl`），但 `wrapperEl` 才是
  未变换的视口矩形来源。
- **`canvasRect` 为普通对象**（非 `DOMRect`），有 `width`/`height`。

## 5. P3：视口事件

| 轮次 | 操作 | 事件总数 | 有效视口变化 | 重复比例 |
|---|---|---|---|---|
| 第一轮 | 3 次平移 + 3 次缩放 + 1 次移动贴纸 | 168 | 未统计 | — |
| 第三轮 | 一次平移 + 一次缩放（分开做） | **84** | **75** | **11%** |

**修正后的结论（第三轮数据推翻了第一轮的解释）**：

1. 补丁驱动可行（首选方案，无需 rAF 轮询）✅
2. 第一轮"6 次手势 168 次回调"当时被解读为"每帧内重复触发，必须去重"。
   第三轮加入去重统计后真相清楚了：**84 次事件里 75 次是真实的视口变化**，重复仅 11%。
   结合"一次手势 ≈ 28 次回调 ≈ 60fps 下 0.47 秒"，可以判定
   **`markViewportChanged` 是逐帧触发的（每帧一次）**，而不是每帧多次。
3. 因此正确的性能要求是：**每帧一次的重绘必须廉价**（分块缓存 + 视口裁剪 + 精灵图集），
   **不能**指望"把多次事件合并成一次"来省开销 —— 那最多省 11%。
   rAF 合并仍要做（防御性、几乎零成本），但它不是性能方案。
4. 那 11% 的重复事件说明**该回调也会因非视口变化而触发**（如节点移动），
   因此去重判据必须是"投影是否真的变化"，而不是"回调是否发生"。
   Phase 1 还需监听节点变化以决定标记层是否重绘。

## 6. 精度与不确定性

- ✅ **`posFromEvt` 的量化已彻底查清**：量子 = **1 CSS 像素**（横纵一致，200 样本/方向），
  与 `devicePixelRatio` 无关。噪声上界 = 0.707 CSS px（二维合成）。见 §2.6。
  插件侧的对策：缩放取矩阵、原点多点标定、运行时走纯闭式路径、判定阈值统一用 `quantumNoiseBound()`。
- ✅ **"0.8 px 差异"的悬案关闭**：那不是模型误差，是噪声。相关判定已全部改为噪声感知。
- ⚠️ **`tx`/`ty` 语义**：第三轮报告显示中心公式的最大偏差 1.55 世界单位 < 量子 3.17，
  于是被判定为"成立"。但这只说明**它与 posFromEvt 在噪声内一致**，
  仍不足以断言"tx/ty 严格等于视口中心的世界坐标"。由于运行时不依赖它，此项**不再阻塞**。
- ⚠️ **跨状态稳定性**：所有结论来自同一个画布。面板尺寸在几轮之间变化过
  （681×724 → 688×730 → 697×736），原点随之从 644.0 → 647.6 → 534.5 变化（属正常现象）。
  侧边栏 / 弹出窗口中的 Canvas、以及跨 Obsidian 版本的行为**尚未探测**；
  诊断命令可随时重跑，成本很低。
