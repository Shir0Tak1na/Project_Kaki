## 关键决定

### 1. 校验策略：结构性错误拒绝，单条目错误跳过

手写的地图不该因为一个坏条目而整份打不开。因此：

- **拒绝加载**（`ok: false`）：不是对象、`version` 缺失/非法、`version` 高于本插件支持、`grid` 不可用；
- **跳过并告警**（`ok: true` + warnings）：地形键不是 `q_r`、未知地形类型、标记缺少 id/坐标、id 重复、
  区域顶点不足 3 个、宽度非法等。每条告警都带精确的字段路径（如 `markers[2].icon`）。

`version` 高于支持时**只读打开、绝不写回** —— 旧版本插件不能把新版字段砍掉。

### 2. 前向兼容：未知顶层字段原样保留

解析时把不认识的顶层字段收进 `extra`，序列化时写在最前（这样已知字段不会被同名的未知字段覆盖）。
测试覆盖了「未知字段经"解析→序列化→再解析"仍在」以及「未知字段不得覆盖已知字段」。

### 3. 序列化格式：每格一行、格内紧凑（实测 28 字节/格）

朴素做法 `JSON.stringify(doc, null, 2)` 实测每格 **42.6 字节**（6400 格 = 273 KB），
而自定义地形序列化把每格压到 **28 字节**：格内不写 `": "` 与缩进，但**仍然一格一行** ——
Git diff 能精确到格，手工改一个格也只动一行。

据此 1 万格约 **280 KB**，落在设计文档 §6 的预估量级内（150–250 KB）附近，可接受。
地形按键（先 `r` 后 `q`）排序，保证 diff 稳定。

### 4. 写入：原子写 + 防抖 + 安全闸

- 用 `vault.process()` 做读-改-写（原子），不用 `read` + `modify` 那种有丢更新窗口的两步写法；
- 编辑期间 `scheduleSave()` 防抖 400 ms，切换视图（`active-leaf-change`）与 `onunload` 时 `flush()`；
- **安全闸**：写入前检查文件里有没有 `type: fictional-cartographer-map` 标记，
  没有就抛错拒绝写入 —— 防止因路径写错把用户笔记覆盖成地图。测试覆盖了"拒绝"与"内容未变"。

### 5. 自写保护按 **mtime** 判断，而不是时间窗

最初的实现是"写入后 X 秒内该路径的 modify 事件视为自写"。这有个真实失败模式：
**外部改动若恰好落在时间窗内会被误判为自写**，导致索引不失效 —— 表现是
"在外面改了绑定关系，插件却找不到地图"。

改为比对 mtime：写入成功后记下该文件的 `stat.mtime`，事件里的 mtime 与之相同才认定是自写，
时间窗只用于清理记录。冒烟测试用"同一路径返回同一 TFile 实例 + 写入更新 stat.mtime + 事件异步派发"
的假 vault 验证了两个方向：自写不触发额外重建、外部改动必须触发重建。

### 6. 索引来自 metadataCache 的 frontmatter

"哪个 canvas 用哪张地图"由地图文档的 `canvases` 列表声明（设计文档 ADR-1：不写 `.canvas`）。
索引在 vault 变更时失效，按需重建。`MapDocumentStore.indexBuildCount` 用于诊断与测试。

### 7. 网格可见范围是**过近似**，但绝不漏

`visibleCellBounds()` 把可见矩形四角转成**分数**轴向坐标后取外包矩形再外扩 margin。
六边形在 q/r 空间里是斜的，所以这会多带一行/一列的格 —— 多画的格由逐格 bbox 判定剔除。
性质测试保证了硬要求：**凡与视口相交的格一定在返回范围内**（多画只影响性能，漏画会直接缺块）。

### 8. 量化误差在按格吸附这一步被吸收

Phase 0 实测 `posFromEvt` 有 1 CSS 像素量化（当前缩放下约 3.17 世界单位），
而格宽 40 世界单位，因此格心附近的抖动不会改变落点格 —— 有单元测试守住这条性质。

### 9. `-0` 归一化（同类问题第三次出现）

`brushCellsAt` 产出的格坐标可能是 `-0`，与 `0` 在 `deepEqual`/`Object.is` 下不等。
`hex.ts` 里已导出 `normalizeZero()` 统一处理，并加了专门的测试断言"落点不以 -0 出现"。

### 10. 覆盖层插为宿主的**第一个**子元素

`div.canvas` 的局部坐标就是世界坐标（实测：各 `canvas-node` 的 translate 正是它在
`.canvas` 文件里的 x/y），所以覆盖层用世界坐标定位即可与原生节点严格对齐 —— 这是策略 A 的直接收益。

插在最前面（而不是追加）是为了让**地形位于地图卡片之下**。相应地 CSS 里**不设 z-index**：
靠 DOM 顺序决定层级，设了反而可能把地形盖到卡片上面。

### 11. 位图分辨率取「视口 × dpr」，缩放时不变

覆盖层的 CSS 尺寸用**世界单位**（父元素的 transform 会缩放它），
位图分辨率固定取「视口 CSS 尺寸 × dpr」，于是最终屏幕像素密度始终 1:1 —— 放大不会糊。
**缩放时位图尺寸不变、只有 CSS 尺寸变化**，这是判断实现是否正确的一条硬指标（已进冒烟测试）。

`deviceScale` 用**精确的 `scale × dpr`**，而不是 `rasterWidth / widthWorld`：
后者会被位图尺寸的整数取整污染（相对误差可达 0.03%），让几何映射不再可预测。
代价是位图被 CSS 拉伸不到 1 px，肉眼不可见。

### 12. 挂载时**同步**画第一帧

最初 `attach()` 只排队一帧（rAF），结果是启用命令报出的统计全是 0，地图也要等下一帧才出现。
改为挂载时直接 `redrawNow()`，之后的变化才走 rAF 合并 —— 既让地图立即出现，也让调用方拿到真实统计。

### 13. 网格线有格数上限

网格线对"对齐校验"和后续绘制都很重要，但缩小到很远时逐格描边会拖垮帧率。
因此可见格数超过 4000 时直接不画网格（地形照画），并把实际画的网格格数记入统计。

### 14. 笔画：**边拖边画**，但历史只记一条

两难：用户要立刻看到笔画效果（所以得边拖边改文档），但撤销又必须一次回到笔画前
（所以不能每格一条历史）。

解法：每条笔画维护一份「格键 → 笔画开始前的状态」映射。
首次触碰某格时记下旧值并立即写入新值（实时反馈）；抬手时据此生成 op 列表（撤销一次到位）。
`opsFromPrevious` 的 `previousOf` 因此必须查这份映射，而**不能**读当前文档 —— 当前值已经是新值了。

### 15. `{ ...null }` 是 `{}`：一个必须显式判空的坑

生成 op 时如果直接写 `previous: { ...previous }`，当 `previous` 为 `null`（该格原本没有地形）时
得到的是 `{}` 而不是 `null` —— 撤销后地图里会留下 `{"t":undefined}` 这类脏数据。
已显式判空，并有专门的测试断言"撤销后不应残留该键"。

### 16. 悬停状态没变化就不重绘

`setHover(null)` 原本无条件请求重绘，而模式同步路径会反复传 `null` ——
每次都白排一帧。现在先比较状态，相同则直接返回（实测 `markViewportChanged` 本身已逐帧触发，
每帧开销必须省着用）。

### 17. 工具条是"锦上添花"，创建失败不应连带地图层失败

`MapLayerManager.enable()` 里把工具条创建包在 try/catch 中：失败只记警告并继续，
地图层照常工作。这个决定是冒烟测试逼出来的 —— 工具条构造函数抛错时，
整个启用流程连同渲染一起失败了，而这个后果与失败原因完全不成比例。

### 18. ⚠️ 根因修正：**DOM 绘制顺序 = 命中测试顺序**，覆盖层收不到指针事件

第一版笔刷"只能在进入绘制模式时单击画一格，拖动无效"。用户最初判断是"拖动被 canvas 的框选功能抢走了" ——
现象正确，但机制更根本：

> 覆盖层为了让地形画在原生卡片**下方**，被插成 `div.canvas` 的第一个子元素。
> 而 **DOM 的绘制顺序与命中测试顺序是同一个** —— 覆盖层同时也是**最底层**，
> 指针事件优先落到它上面的元素（背景 SVG、边层 SVG、各 `canvas-node`、以及带框选处理的 canvas 元素）。

因此"把覆盖层设成 `pointer-events: auto` 来接收绘制手势"从根上就是错的：
初始那一次 `pointerdown` 只是碰巧命中，拖动过程中的 `pointermove` 全部被上面的元素接管
（Obsidian 的 canvas 还会对指针做 capture，进一步把后续事件锁在它自己身上）。

**修复**（`src/editor/MapInteraction.ts` 重写）：

1. 在**视图容器**（`view.containerEl`，比 `wrapperEl` 与 canvas 元素都高）上用
   **捕获阶段**监听 `pointerdown` —— 捕获阶段自外向内，因此我们的处理**先于** Obsidian；
2. 绘制模式下对左键 `preventDefault + stopPropagation + stopImmediatePropagation`：
   原生框选/拖拽在启动瞬间就被拦下；
3. 用 `setPointerCapture` 把整条手势交给自己，拖动中的 `pointermove` 稳定到达；
4. **中键/右键不拦**，原生平移照旧；滚轮完全不碰，缩放照旧；
5. 覆盖层的 `pointer-events` **永久保持 `none`** —— 它只负责画，不再参与命中测试。

这个顺序上的矛盾是本项目最容易复发的一类错误，已固化成回归测试：
"覆盖层始终保持 `pointer-events: none`"、"指针监听挂在视图容器上"、
"选择模式下左键不被拦截"、"地图视图之外的事件不被拦截"。

### 19. 撤销冲突：按键作用域跟着**焦点**走

`Mod+Z` 曾与编辑器的撤销打架。Obsidian 的作用域栈是后进先出，只有位于栈顶才先到我们手里。
现在：

- canvas 成为活动视图时（`active-leaf-change`）把作用域移到栈顶；
- 其它视图获得焦点时**弹出**作用域 —— 在编辑器里按 `Ctrl+Z` 撤销文本才是用户预期；
- 点击画布时也提一次（焦点从编辑器挪到画布不一定触发 `active-leaf-change`，靠这一步兜底）；
- 绘制模式下才接管 `Mod+Z`；选择模式下返回 `true` 交还给 Obsidian（原生节点撤销）。

同时按"都做进 UI"的思路，工具条上的**模式切换 / 地形 / 笔刷 / 撤销 / 重做**都是按钮，
不依赖焦点与作用域栈 —— 它们是这些操作的可靠入口。

### 20. 捕获阶段拦截必须排除**同一容器里的 UI**

修完 §18 之后出现两个新问题：**工具条按钮点不动**、**绘制状态下 Obsidian 的缩放控件等 UI 也点不动**。
两者同源：工具条与 Obsidian 的画布控件（`.canvas-controls`、`.canvas-card-menu`）都位于
`wrapperEl` 里，也就是位于我们的捕获宿主（`view.containerEl`）之内 ——
捕获阶段的 `stopImmediatePropagation` 把点击整个吃掉了，事件根本到不了按钮。

修法：拦截前先判定目标是否是 UI：

- `getUiExclusions()` 显式传入我们的工具条元素；
- 再加一张 Obsidian 画布控件的选择器表（`.canvas-controls` / `.canvas-card-menu` / `.canvas-menu` / …）；
- **绘制过程中不做 UI 判定**：指针扫过工具条时笔画不该断。

回归测试直接覆盖这两条：工具条上的 `pointerdown` 不被拦截、点击工具条能切换地形且不落笔、
Obsidian 画布控件不被拦截。

### 21. ⚠️ 自写保存触发重载 → 撤销历史被清空（"画完一秒后撤销自己变灰"）

链路：笔画结束 → 400 ms 防抖保存 → 文件写入 → vault 的 `modify` 事件 →
处理函数把文件**重新加载**并调用 `resetForNewDocument()` **清空历史**。
时间正好对上"大约一秒后"。自写保护只加在了存储层的索引失效上，没加在这条重载路径上。

两处修复：

1. **重载不再清空撤销历史**（结构性修复）。历史里的 op 记录的是"格 + 新旧状态"，
   对替换后的文档**依然成立** —— 清空它反而让用户在保存后失去撤销能力。
   这样即使自写识别失效，也不会丢历史。
2. 自写事件**跳过重载**（用存储层基于 mtime 的 `isOwnWrite`）。
   刻意**不用时间窗**：时间窗会把紧随其后的**真实外部改动**吞掉 —— 这个坑在 §5 已经踩过一次。
   另外**绘制中不重载**，否则进行中的笔画会写进被替换掉的旧文档。

回归测试：落笔 → 落盘 → 等 modify 事件 → 断言历史仍在、文档没被换掉、撤销可用；
对照组：外部改动**应当**重载进来，但历史同样保留。

### 22. 标记与文字标注：**DOM 挂在未变换的 wrapperEl 上**

地形走 canvas（量大、批量绘制），标记与文字走 DOM（需要 hover/点击/可访问性，且字号不能随缩放糊）。
但标记层**不能**放进 `div.canvas` —— 那会被父元素的 transform 缩放，文字会跟着放大缩小。
因此它挂在**未变换的 `wrapperEl`** 上，每帧由投影算出屏幕坐标（billboard）：

- 位置用 `translate3d(x, y, 0)` 更新（走合成层，不触发重排）；
- 锚点：标记是"针"（`translate(-50%, -100%)`），文字是中心（`translate(-50%, -50%)`）；
- 文字字号 = 世界字号 × 缩放，clamp 到 [11, 28] px；
- **只渲染视口内（外扩 160 px）的条目** —— DOM 规模只与可见数量有关，与地图总量无关；
  留白是为了避免边缘反复创建/销毁元素。

同帧调度：标记层由 `MapOverlay` 在同一个 rAF 里同步，因此地形与标记不会脱节。

### 23. 三个"必须显式处理"的交互细节

1. **点击 vs 拖动**：标记/文字在 `pointerup` 时才放置，且要求按下与抬起几乎没移动（≤4 px）——
   否则一拖动就会放出一片标记。
2. **标记的交互开关**：绘制模式下标记层 `pointer-events: none`（此时点击的意思是"在这里放新的"），
   选择模式下才可点（打开笔记）与右键删除。这个开关挂在**编辑器的 `onStateChanged`** 上，
   而不是只挂在"经过交互层的模式切换"上 —— 后者会漏掉绕过交互层的模式变更（冒烟测试抓到过）。
3. **图标缺失的降级**：Lucide 图标名跨版本可能变。渲染前先用 `getIcon()` 校验，
   取不到就退回一个中性圆点（CSS 伪元素），而不是**什么都不显示** —— 图标缺失不该让标记"消失"。

### 24. 放置对话框留了注入接缝

`PlaceModalFactory` 可被替换（插件上有 `setPlaceModalFactory`）。
默认是真实的输入对话框；自动化测试注入替身直接提交固定内容，于是
"点击 → 对话框 → 写入文档 → 渲染 → 点击打开笔记 → 右键删除 → 撤销"这条链可以端到端验证。
将来做批量导入（从 CSV / 笔记属性生成标记）也会用到同一个接缝。

### 25. 两个用户反馈的修复 + 一个自己埋的隐患

**① 文字标注删不掉**：`MarkerLayer` 里只给标记注册了 `contextmenu`，文字标注那条分支**漏了**。
现在标记与文字共用同一个 `attachInteraction()`，不会再各写一份而漏掉某个监听。

**② 标记放好之后不能移动**：这是**缺功能**，不是 bug —— 我只做了放置，没做拖动。
现在选择模式下可以**按住拖动移动**标记与文字：

- 新增 `moveMarker` / `moveLabel` op（`from`/`to` 都记在 op 里，逆操作就是交换两者）；
- 与笔画同样的思路：拖动中实时改文档（跟手），抬手才压成**一条**可撤销的历史；
- 标记在抬手时**吸附回格心**（与放置一致），文字保持自由位置；
- 位移小于阈值时**不入历史**（避免"点一下就多一条撤销"）；
- 拖动结束后抑制紧随其后的 `click`（否则拖一下会顺带打开笔记）。

**③ 标记层容器会挡住原生画布**（自己埋的隐患，写测试时发现）：
`setInteractive(true)` 原本把**容器**设成 `pointer-events: auto`，而容器铺满整个视口 ——
那会让选择模式下的原生点选/拖拽全部失效。现在只切容器上的 class，
由 CSS 决定"**仅实体元素**可点"，容器永远穿透。这条已固化成回归断言。

### 26. 顺手修掉的性能问题：网格线整帧只描边一次

调试输出里看到一个数字：**一帧画了 1209 个网格格**。原实现每格一次 `beginPath + stroke`，
在缩小状态下就是上千次描边调用。改成整帧**一条路径、一次 `stroke()`** ——
相邻六边形的边本来就重合，合并后既更快，视觉上也更干净。
冒烟测试把"整帧描边次数 ≤ 2"固化为断言。

### 27. 路径与区域：草稿只在内存里，提交才产生一条历史

多点图形（河流、道路、国家边界）的手势是"逐点点击定顶点 → 结束"。
关键的三个决定：

1. **草稿不进文档**。顶点先攒在编辑器内存里，`finishDraft()` 才生成一条完整 op ——
   于是撤销一次就是整条撤掉，绘制途中也不会反复触发保存与重载。
2. **结束有四个入口**：双击（同位置 350 ms 内两次按下）、回车、右键。
   三者都保留是因为它们各有失效场景：双击依赖时序、回车需要焦点、右键受原生菜单影响。
   **Esc 的语义是"退出当前这一步"**：有草稿时先取消草稿，没有草稿时才退出绘制模式。
3. **顶点不足就放弃**（路径 < 2、区域 < 3），且**不入历史** ——
   否则"点了两下再按回车"会留下一条什么都没做的撤销记录。

### 28. 草稿预览必须与最终渲染用同一套几何（WYSIWYG）

第一版预览画的是**折线**，而提交后的河流是**平滑曲线**：松手的一瞬间形状会突变。
现在 `MapDraft` 带上 `smooth` / `taper`，预览与最终渲染走同一个 `buildSmoothCommands()` ——
所见即所得。这条是被冒烟测试逼出来的（断言"预览里有 bezierCurveTo"时才发现预览根本没走曲线）。

### 29. 右键删除形状：只能自己做命中测试

标记与文字是 DOM 元素，右键靠事件目标就能定位；**路径与区域画在 canvas 上，没有事件目标**，
因此必须做几何命中测试（`hitTestShape`：先测路径的线宽范围，再测区域的多边形内外）。

两个细节：

- 命中才拦截：**右键空白处一律放行**，原生菜单照常弹出（冒烟测试覆盖了两个方向）；
- 路径优先于区域：绘制顺序是"区域在下、路径在上"，删除时也按同一顺序，
  避免点了河流却删掉下面的大区域。

### 30. 河流变宽：canvas 不支持变宽描边，按段画

canvas 的 `lineWidth` 是整条路径统一的，因此河流的"末端变细"实现为**逐段描边**、
每段不同线宽，段间用圆头连接（`lineCap: 'round'`），视觉上连续。
代价是每段一次 `stroke()`，但河流顶点数通常在几十以内，可以接受。

### 31. 路径与区域的名称：三个锚点问题

用户提出"能不能为区域和线条命名"。名称本身是一个字段（`MapPath.label` / `MapRegion.label`），
麻烦的是**画在哪里**：

- **路径用"按弧长的中点"，不用"中间那个顶点"**。顶点分布不均时（例如一段长直线加一小段引线），
  中间顶点会明显偏向一侧；弧长中点始终落在线条的视觉中部。
  有测试钉死这一点：`(0,0)-(1,0)-(101,0)` 的弧长中点是 `x=50.5`，而中间顶点是 `x=1`。
- **名称要沿法线推出线宽之外**。否则文字直接压在河流上，深色地形上几乎不可读。
  法线取切线旋转 90°，若朝下就翻到上方（`normalY > 0` 时取反），避免文字压住下方的线。
- **区域用面积质心，但质心落在凹多边形外时要退化**。"∩"形（上边一条横带 + 两条腿）的质心
  落在缺口里 —— 直接画上去名称就跑出形状之外了。`polygonAnchor()` 先试质心，
  落在外面就在包围盒内网格采样，取"在多边形内且离质心最近"的点。
  测试用这个「∩」形做了对抗性断言：质心必须被判为在外，最终锚点必须在内，且不能等于顶点平均。

文字本身用 **描边光晕**（先 `strokeText` 深色粗边，再 `fillText` 白色）：
地形背景颜色不可控（深绿、沙黄、雪白都有），单靠填充色无法保证可读。

### 32. 命名走"普通 op"，因此天然可撤销

命名不是元数据旁白，而是一条可撤销的编辑：`renamePath` / `renameRegion` 记录 `from`/`to`，
逆操作交换两者。两个边界情况：

- **路径的"清除名称"是删字段**（`delete path.label`），区域是置空串 ——
  因为 `MapRegion.label` 是必填字段而 `MapPath.label` 是可选的。反向操作都能精确还原，
  测试对"有名字 → 清除 → 撤销"和"没名字 → 命名 → 撤销"两个方向都做了往返断言。
- **命名与绘制各占一条历史**（不是合并成一条）：用户如果只是不想给名字，撤销一次就能回到"没命名"，
  而绘制那一步仍然独立可撤销。

### 33. 画完立刻弹命名框：形状已经提交，留空**不删形状**

绘制结束时（双击 / 回车 / 右键）草稿已经提交进文档，命名框只是"顺手命名"。
因此留空提交的语义是**跳过命名**（按钮文案也写"跳过"而不是"取消"），
而不是"取消这次绘制" —— 后者会让用户以为白画了。

选择模式下**双击形状**是重命名入口；在那个场景里留空表示**清除名称**。
两处复用同一个 `TextPromptModal`（新增 `allowEmpty` 与"跳过"按钮），
并在 `MapLayerManager` 里统一处理：弹框是异步的，回调里**必须重新取一次 entry**
（期间视图可能已被关闭），不能闭包捕获旧的 editor。

### 34. ⚠️ 回归：为了加"双击重命名"而把中键平移吃掉了

选择模式的双击分支是**新插入**的代码，我把它放在了

```ts
if (editor.mode !== 'paint') return   // 原来在这里
if (event.button !== 0) return        // 和这里
```

**之后**。TypeScript 立刻报错（`'paint'` 与 `'select'` 没有重叠），
我把守卫删掉重排，顺手把 `if (event.button !== 0) return` 一起删了 ——
于是**绘制模式下中键（原生平移）被捕获阶段吞掉**。

这个错误只被冒烟测试里一条既有断言（"中键不被接管"）抓住，TS 不会报。
教训：重排守卫时，删掉的每一行都要确认它是否**在别处仍然生效**；
`if (event.button !== 0)` 这种"放行分支"删掉后不会报错，只会静默改变行为。

### 35. 名称显示开关：只影响绘制，不进文档

`MapEditor.showShapeLabels` 是一个**视图状态**：元素密集时用来降噪，
刷新后恢复默认（打开），不进文档、不进历史、不需要保存。
绘制侧只在 `MapOverlay` 一处消费（`getShowShapeLabels`），
`drawRegion` / `drawPath` 的 `showLabel` 参数决定是否画文字。

顺带一提，这个开关接进 `MapLayerManager` 时我第一次**漏了接线**：
`MapOverlay` 有 `getShowShapeLabels` 选项，但 `MapLayerManager` 没传，
开关点了没反应 —— 是场景 16 的冒烟断言（"隐藏名称后不画任何形状文字"）发现的。

### 36. 无修饰键的快捷键必须自己让行给输入框

我们的画布快捷键是**无修饰键**的字母（`p` / `r` / `b` / `m` / `t` / `d`、数字、方括号）。
Obsidian 的 `Modal` 打开时确实会把自己的作用域压到栈顶，但**它只注册自己用到的键**；
未命中的按键会继续沿作用域栈往下走 —— 也就走到了画布作用域。

结果就是：命名对话框里打「北境**r**oad」时，`r` 会顺手把工具切成区域。

修法是在自己的注册包装里统一加一道守卫：**事件焦点落在 `input` / `textarea` / `select` /
`contenteditable` 上时返回 `true`（= 未处理，继续向下传递）**。
按 Obsidian 的 `Scope` 约定，`false` 才是"我处理了、别再往下传"，因此这里的返回值不能写反。

冒烟测试对两个方向都做了断言：输入框里按 `P` **不**切换工具且返回 `true`，
而画布上按 `P` 照常切换并返回 `false` —— 后者防止把守卫写成"一律不响应"。

### 37. ⚠️ 真实反馈：名称过小、名称不随线条走、河流变折线

三条都是在真实 Obsidian 里画出来才暴露的，桩环境全部测过却全都没测出来。逐条记：

#### (a) 河流提交后变成折线 —— 变宽分支直接连了原始顶点

```ts
// 错误版本
if (path.taper === true) {
  const widths = taperedWidths(path.width, points.length - 1)  // points = 控制顶点！
  for (...) { moveTo(points[i]); lineTo(points[i + 1]); stroke() }   // 直弦
}
```

河流是"平滑 + 变宽"，而 **canvas 的 `lineWidth` 是整条路径统一的**，
所以变宽只能逐段描边；逐段描边时我图省事用了**控制顶点**，
于是预览里看到的是平滑曲线（预览走 `bezierCurveTo`），提交后画出来的是折线。

修法是把曲线**展平**成稠密折线（`flattenCommands` + `flattenSteps`）再逐段描边，
并新增 `visiblePolyline()` 作为"看得见的几何"的唯一来源 ——
描边、名称排版、命中测试现在都用它（命中测试之前用控制顶点，急转弯处会点不中）。

> **为什么原来的测试没抓住**：那条断言是 `ctx.calls.stroke >= 2`（"逐段描边了"）。
> 它测的是**实现细节**（调用次数），不是**几何**。现在冒烟桩会记录每个路径段的坐标，
> 断言改为"最大单点转角 < 15°"——折线在直角处必然出现 ~90° 的尖角，
> 拿旧的 main.js 跑新断言会**立刻失败**（我用旧产物验证过这一点）。

#### (b) 名称过小 —— 字号公式的下限变成了实际字号

```ts
Math.max(11, Math.min(26, 16 * scale)) * dpr     // scale 0.4467 → 11 CSS px
```

常见缩放（约 45%）下 `16 × scale ≈ 7`，所以"下限 11"**就是用户看到的字号**。
而 11 px 在真实地图上确实太小（连标记文字标注也是同一个下限）。

新公式：`round(clamp(base × scale, min, max)) × dpr`，路径 `22/15/34`、区域 `26/16/36`。
两点值得注意：

- **取整的是 CSS 字号**再乘 dpr。反过来取整位图像素会让"至少 16 px"变成 15.8 px
  （冒烟断言就是这么发现的）。
- 顺带把标记/文字标注的下限从 11 提到 13：它们在同一张图上，视觉上应当同一档次。
  （这一条是**未被要求**的一致性改动，容易回退。）

#### (c) 名称不随线条走 —— 从"整体旋转"改为逐字沿弧长摆放

第一版只把整串文字按中点切线旋转一次。用户要的是"顺着路自动适应"，因此改成
**逐字沿弧长摆放**：每个字取自己所在弧长处的位置与切线，各字独立旋转。

四个必须处理的细节：

1. **阅读方向**：路径可能是从右往左画的。先按首尾弦判定方向，必要时把折线整体反转，
   否则字的左右顺序会反过来（"北境"变"境北"）。
2. **不让字倒着**：切线朝左时角度翻 180°（`cos < 0`），保证每个字都是正的朝向。
3. **文字比线条长**：放不下就退化为"整段旋转一次"，总比挤成一团或溢出线外好。
4. **间距按弧长**：直线距离在弯曲处会被缩短（90° 拐弯处 8.3 px 的弧长对应 7.0 px 的弦长），
   因此冒烟断言算的是**弧长**上的间距。

## 测试写法上的一条教训

写"拖动插值"的断言时，我最初硬编码了期望格号（以为世界坐标竖直向下就是 `0_0 → 0_1 → 0_2`）。
实际失败并暴露出：**世界坐标竖直向下在六边形网格里是斜穿的**（q/r 交替步进），
真实路径是 `0_0 → 0_1 → -1_1 → -1_2 → …` —— 代码是对的，断言是错的。

改为断言真正关心的性质后更稳：**笔迹必须是连通的**（用六边形距离做图连通性检查，能直接抓住"断线/空洞"），
以及**终点格必须落在笔迹内**（终点格由几何现场算出，不硬编码）。

## 第二条教训：断言"实现细节"会漏掉真实缺陷

这一轮最有价值的收获是同一个坑的第二次出现（§37a）：

| 我写的断言 | 它实际测的是 | 漏掉了什么 |
|---|---|---|
| `ctx.calls.bezierCurveTo > 0` | 预览**用了贝塞尔命令** | 提交后的渲染走的是另一条分支 |
| `ctx.calls.stroke >= 2` | 河流**逐段描边了** | 逐段的两个端点用的是控制顶点 → 折线 |
| `ctx.calls.fillText === 2` | 画了两次文字 | 名称改逐字排版后这个数字失去意义 |

三条全绿，而用户在屏幕上看到的是**折线**。根因是断言停在"调用了几次某个 API"，
而用户看到的是**几何**。修法：让冒烟桩记录**每个路径段的实际坐标与每个字形的实际位置/旋转角**，
断言改成几何性质（最大转角、弧长间距、字号 CSS 值、旋转角是否随曲线变化）。

一个副产品证据：**用旧产物跑新断言会立刻失败**（最大转角 90°、字号 10.9 px、字形 2 个）。
如果新断言在旧产物上也能通过，那它就没有在防这个缺陷。

## 第三条教训：拿不准的视觉参数，不要靠改常量去猜

"名称过小"连续两轮反馈都没解决（11 px → 15 px 都被判为"很小很小"）。
这说明**问题多半不在那个常量上**：我一直在猜"多大才够"，而屏幕上的真实比例无法从这里确认。

于是这一轮换做法：

1. **换算改成实测**（`MapOverlay.measureRasterScale()`）。位图尺寸是我们设的，但它在屏幕上占多少
   CSS 像素由浏览器决定（元素 CSS 尺寸 × 祖先 transform）。以前我用
   `fontBitmapPx = cssPx × devicePixelRatio` 反推，等于在赌"位图比例 = dpr"这个模型；
   现在直接量 `canvas.width / canvas.getBoundingClientRect().width`。
   任何模型偏差都会被这一步吸收 —— 承诺"N 个 CSS 像素"就必须是 N 个 CSS 像素。
   冒烟里有一条对抗性断言：把"屏幕尺寸"量成一半，字号必须翻倍。
2. **把旋钮交给用户**：设置里加「路径与区域名称的字号」滑块（0.5×–3×，立即生效、落盘）。
   视觉偏好应该由看得见的人决定，而不是由我在代码里猜。
3. **把数字报出来**：状态命令与设置界面都显示
   "路径 24 px · 区域 28 px（倍率 ×1）· 标定 1 CSS px = 1.65 位图像素"。
   下一轮反馈只要贴这一行，就不必再描述"小"了。

顺带把下限抬到**路径 20 px / 区域 24 px**（此前 15/16），
并把同一张图上的标记文字标注下限从 13 抬到 15，保持一致。

**元教训**：当一个参数我判断不了、用户只能描述感受时，
先把它变成"可读的数字 + 可调的旋钮"，再谈调多少。

## 第四条教训（最贵的一条）：`ctx.font` 里不能写 `var()`

"名称过小"改了两轮都没解决，第三轮用户给了一个决定性线索：

> 调整滑块，字体只有阴影在变化。

阴影（光晕）的宽度是 `lineWidth = fontPx / 5` —— 一个**普通数值属性**；
而字形大小取决于 `ctx.font`。**只有前者变化**，说明 `ctx.font` 的赋值根本没生效。

根因：

```ts
ctx.font = `600 ${fontPx}px var(--font-interface, sans-serif)`   // ← 整条声明非法
```

`ctx.font` 是 CSS `font` 简写，而 **`var()` 在画布上没有元素上下文可供替换** ——
写了变量，整条声明非法，而非法赋值的后果是**静默忽略**：画布继续用上一个字体，
初值是默认的 `10px sans-serif`。

于是症状全都对上了：

| 观察到的现象 | 解释 |
|---|---|
| "字还是很小很小" | 一直是默认 **10 px 位图像素 ≈ 6 CSS px**，和我设的 11/15/20 px 全都无关 |
| "改字号常量没用" | 常量确实算对了，只是从来没被画布接受 |
| "虽然会跟着比例缩放" | 缩放大时 `fontPx` 变大 → 光晕变粗 → 看起来"变大了一点" |
| "调整滑块，字体只有阴影在变化" | 只有 `lineWidth` 生效了 |

修法两步，缺一不可：

1. **字体族要解析好再传进来**：`getComputedStyle(container).fontFamily`
   （真实、已解析的字体列表），而不是写一个 `var()`。
2. **赋值后读回校验**：把 `ctx.font` 读回来解析字号，与想要的值不符就退到
   `sans-serif` 重写一次。宁可字体族不跟随主题，也不能让字号悄悄退回 10 px。

冒烟桩现在**复刻浏览器的这条规则**：`font` 用带校验的存取器，含 `var()` 的赋值直接丢弃，
并记录每一次尝试。加上这条规则后，修复前的产物会挂 **7 条断言**
（"实际字号 = 策略字号 × 实测标定"直接把默认的 10 px 报出来）。

**元教训（两条）**：

- 静默失败的 API（无效赋值被忽略、不抛错）必须**读回校验**。
  这和 §37c 的"实测标定"是同一招：不要假设，去量。
- **用户的现象描述比我的模型更可靠**。"只有阴影在变化"这一句直接指出
  "数值属性生效、字体属性没生效"，比我自己推导十遍换算关系都有效 ——
  前两轮我一直在调那个**根本没被读到的**常量。
